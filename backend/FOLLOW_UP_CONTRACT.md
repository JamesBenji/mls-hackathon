# Follow-up integration contract

## Immediate one-off calls

`POST /follow-up-plans/{id}/call` requires `{approved:true,revision:int,expected_phone:string,request_key:string}`. The request key must be a fresh random 16–128 character alphanumeric/underscore/hyphen value per explicit approval, reused for retries. A repeated key returns the original dispatch, never another call. The plan may be draft, active or paused, provided it has generated questions and instructions; explicit confirmation approves that revision for this call only. Finished plans are rejected. Approval is scoped to the displayed plan revision and destination number. The draft/paused/active state, recurrence and next scheduled slot are not changed. The call receives one attempt only: automatic retries, resumption and callbacks are disabled for that session.

Guardian Main now contains the reviewed plan-driven photo workflow. Leave `ELEVEN_IMMEDIATE_CALL_BRANCH_ID` empty to use Main; an explicit value overrides the branch for staging. Calls use that agent's configured duration, with no extra one-minute cap. An optional API `max_duration_seconds` override accepts 15–3600 seconds and requires provider override permission; it is not sent by the desktop. Photo tools continue to require the generated session credential and approved photo policy. No agent provisioning runs automatically.

The response remains the plan detail dictionary with an additional `call_dispatch` containing `call_session_id`, `status`, `mock`, `max_duration_seconds`, and `single_attempt`. A provider error is recorded as `dispatch_unknown` and blocks new calls for that patient until the provider result is reconciled; do not assume failure means no call occurred. An already pending/ongoing call blocks a second approval. History exposes `mock` separately from operational status. Shared service-key authentication remains unchanged and is not identity-bound doctor authorization.

## Patient creation and photo review

`POST /patients` accepts `{doctor_id,name,phone}` and creates a minimal patient for an existing doctor, normalizing the phone to E.164. The desktop exposes this inside New plan → New patient. `POST /patients/{id}/pairing-token` accepts `{doctor_id}` and issues a patient-scoped bearer credential with a no-store response. This route is a trusted service-key operator bootstrap with the same shared-key limitations as other dashboard operations, not doctor login. Transfer the credential privately to the phone app before attempting push/photo collection.

Plan details include `photo_requests` associated through the call session and each call's latest `transcript`. The dashboard fetches image bytes using service authentication at `GET /follow-up-plans/{id}/photos/{photo_id}/content`; this route verifies the photo belongs to a call in that plan and returns private/no-store content. Technical quality feedback is advisory, separate from diagnosis and clinical approval. The desktop refreshes selected results every eight seconds while connected and idle.

Backend reconciliation supersedes `feat/medgemma-elevenlabs` while retaining its Gemma 4 cloud gateway and existing patient/clinical schema. No ElevenLabs configuration is provisioned or changed. The old provisioning entrypoint now refuses to run.

## Dashboard

All routes below use existing `X-API-Key: GUARDIAN_API_KEY`. A shared guardian key is service authentication, **not doctor identity**: the backend verifies patient/plan doctor associations but cannot prevent a key holder from selecting another doctor ID. Do not expose this key publicly or describe this as multi-tenant doctor authorization. Use a trusted server proxy until identity-bound auth is implemented. Existing patient routes remain available; an existing doctor and patient identity are sufficient, no medical-record entry required.

`GET /follow-up-plans` returns an array of plan dictionaries; optional `doctor_id` filters the array. `POST /follow-up-plans/draft` accepts `{doctor_id:int,patient_id:int,instructions:string}` and returns a plan dictionary with status `draft`. An ambiguous/empty draft returns HTTP 422 with a clarification string in `detail`; model unavailability returns 503. Generation never schedules or calls.

`PATCH /follow-up-plans/{id}` accepts any subset of `instructions:string`, `context:string`, `questions:string[]`, `tracked_items:TrackedItem[]`, `photo_policy:"none"|"first_call"|"every_call"`, and `schedule:{timezone:string,local_time:"HH:mm",frequency:"once"|"daily",start_date:"YYYY-MM-DD",end_date:"YYYY-MM-DD"}`. Null fields are rejected; omit unchanged fields. A meaningful edit increments `revision`, cancels pending work and returns the plan to `draft`. Finished plans cannot be edited. Changing `instructions` regenerates the interpretation/questions/tracking/photo policy via Gemma on the same plan; display that readable interpretation for review. The doctor writes natural language only: no template selection or schema editor is needed.

`POST /follow-up-plans/{id}/activate`, `/pause`, `/finish`, and `/call` return the updated plan dictionary. `/call` requires an active plan and includes recent calls. `GET /follow-up-plans/{id}` also includes recent calls/results. Draft/paused/finished calls return 409; incomplete activation returns 422. Activation is the doctor's explicit approval of the displayed instructions, context, questions, tracked items, photo policy, and schedule. Draft output must be reviewed; it is not automatically clinically trusted.

Plan dictionary: `{id,doctor_id,patient_id,patient_name,instructions,context,questions,tracked_items,photo_policy,schedule,status,next_call_at,last_summary,revision}`. Status is `draft|active|paused|finished`; `schedule`, `next_call_at`, and `last_summary` may be null. Detail adds `calls:[{id,call_session_id,status,started_at,summary,results}]`, newest first (up to 10), and `observations` as described below. Call `results` and `summary` are AI draft report interpretation, NOT the patient-report observations. Timestamps are ISO naive UTC, matching existing APIs. No credential is returned in a plan dictionary.

`TrackedItem` is `{id:string,label:string,type:"number"|"boolean"|"choice"|"text"|"photo",unit:string|null,min:number|null,max:number|null,options:string[]}`; `options` defaults to an empty list. Legacy string labels are tolerated as text items. Definitions are local to this plan, not global patient fields. Gemma derives them from instructions and asks clarification rather than inventing consequential units/scales. `min`/`max` are explicitly instructed scale bounds, not invented clinical alert thresholds. IDs survive label-only edits; changing type/unit/bounds/options forks the ID. Revisions increment on other meaningful edits too.

Detail `observations` is an array of `{id,item_id,plan_revision,call_session_id,value,status,unit,source_quote,reported_at,measured_at,definition_snapshot}`. Status is `reported|missing|unclear|declined`; value is a number, boolean, string or null. Each call snapshots its approved definitions/revision. Postcall Gemma extraction is validated against those definitions, exact patient-source quotes, types, finite numbers, units, ranges and choices; invalid reports become `unclear` with null value. Missing items are explicit nulls, never zero or interpolated. Extraction failure produces unclear/null observations. Unknown IDs are ignored. `reported_at` is the call end/receipt time; `measured_at` stays null unless an explicit exact ISO time appears in the patient's quote. A single photo tracking item can reference a verified uploaded asset ID, never an inferred image from speech; multiple photo-item attribution and uploads arriving after postcall extraction are not automatically resolved. Old observations and definition snapshots remain immutable after edits. Graph only compatible item IDs/revisions/units, keep gaps, and label these as extracted patient reports, separate from AI summary/interpretation.

Schedules use IANA zones and 24-hour times, inclusive date bounds, at most 366 days; `once` requires identical start/end dates. Nonexistent DST wall times are skipped; ambiguous times use the first occurrence. Activation requires a future occurrence. Server schedules one occurrence at a time, consumes a due slot before dialing, skips slots over one hour late, and never replays a daily backlog. A failed placement consumes that slot; the existing bounded retry/callback logic handles started calls. `active` may have null `next_call_at` after its final slot, until the doctor finishes it. `/call` is an explicit extra immediate call and does not consume the next scheduled slot. Pause/finish do not hang up a call already in progress, but block future resumes and photo tools. Run one scheduler-enabled API worker; a general distributed task system is intentionally out of scope.

The legacy `POST /agent/jobs` now creates a pending CallJob plus a draft FollowUpPlan, returning `plan_id` alongside its existing response. Extracted time is retained as a proposal, never scheduled. The existing authorized `/agent/jobs/{id}/start` is explicit one-shot review/approval of that job/linked plan and starts immediately, without a recurring schedule; paused/finished plans and already-started jobs are rejected. Prefer the plan review/activation flow for new UI work. Existing explicit `/calls/start` remains a privileged compatibility endpoint, not an automatic generation path.

## Voice tools and phone app

The five live variables remain `patient_name`, `question_plan`, `last_call_summary`, `session_id`, `resume_from`. Plan calls use an approved plan snapshot, plan-specific last summary and checkpoint, without generating extra live interview questions. Legacy explicit job calls now retain situation/treatment context. Additional runtime fields are `secret__photo_tool_authorization` (the **full** `Bearer <per-session-secret>` header value) and `photo_request_key` (send as `Idempotency-Key`). Runtime fields are sent per call, not written to the live agent configuration or exposed in plan APIs. Credentials are stored only as hashes, rotated on resume, expire after four hours, and are accepted only for the current in-progress conversation and active approved plan. `first_call` permits photos only in the first session of that plan (callbacks share that session); `every_call` permits each session.

`POST /tools/request_photo` body: `{session_id:string,conversation_id:string,instructions:string}`. Headers: `Authorization: <secret__photo_tool_authorization>` and `Idempotency-Key: <photo_request_key>`. `POST /tools/check_photo_status` body: `{session_id:string,conversation_id:string,request_id:string}`, with the same Authorization. Responses contain `{request_id,push_status,status,technical_feedback:string[],retake_optional?:true}`. Quality status is `waiting_for_upload|checking|clear_enough|retake_recommended|uncertain|failed`; feedback is restricted to technical codes `blur|too_dark|glare|framing|too_far|obstructed`, never diagnosis. Wrong credentials return 401, association/policy violations 403, wrong request 404, conflicting idempotent input 409. One durable photo request per session is reused across retries/callbacks. FCM is best effort; patient polling is authoritative.

Existing bearer-authenticated phone routes are unchanged: `/me`, `/me/devices/{device_id}`, `/me/photo-requests`, `/me/photo-requests/{id}`, and multipart upload `/me/photo-requests/{id}/photos` with `Idempotency-Key`. Request output now adds `quality:{status,technical_feedback,retake_optional?}`; its existing `status:pending|completed` remains the upload lifecycle, not quality. Upload is accepted immediately and starts a separate asynchronous Gemma image-quality task. Quality is advisory: original content remains available even when uncertain/failed. A retake after `retake_recommended|uncertain|failed` uses the same request and a new upload idempotency key; it replaces the current asset bytes only after successful persistence. The old file is then removed. No historical-retake gallery is implemented. A restarted/interrupted quality task becomes `failed` after five minutes when polled; a retake remains possible. Quality failure never rejects an upload.

## Safe setup and rollout

From `backend/`, back up the database and private photo directory, stop the old scheduler, then run `python -m scripts.setup_followups` (read-only preflight) and `python -m scripts.setup_followups --apply` (create missing tables only). Reconciliation adds `follow_up_plans`, `follow_up_plan_calls`, `follow_up_observations`, `photo_tool_requests`, and `photo_quality_checks`; no existing column is changed. Startup `create_all` also creates these missing tables, but **cannot add missing columns to an older colleague schema**. Preflight detects that condition and stops; prepare reviewed additive ALTER statements for that actual deployed schema before proceeding. Never run the destructive demo seed against existing data. Run preflight before deploying to any database that ran an intermediate version of this branch, too.

Before restart, review/remove old `job:*` scheduled entries produced by the previous automatic extraction flow; those lack doctor approval and are now refused at execution. Existing plan jobs and resumes recheck approval at execution. Do not run provisioning: live agent/tools/model/voice/phone configuration is authoritative. Verify staged photo-tool runtime/header bindings manually without applying historical defaults. Keep production keys out of logs and client bundles. Local smoke tests use mock telephony, fake model output and disabled FCM; live phone/FCM/model end-to-end behavior still requires a reviewed deployment test. The inherited doctor notification hook remains a placeholder (now metadata-only logging), not a guaranteed delivered clinical alert.
